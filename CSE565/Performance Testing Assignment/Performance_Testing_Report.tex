\section{Task 1: Identification of the Performance Testing Framework}

Locust 2.46.6 was selected as the performance-testing framework. Locust is a Python framework in which a user class defines the work performed by a simulated user. It records request count, failures, response times, response-time percentiles, and requests per second (RPS). The framework can be run from the command line in headless mode and can create HTML and CSV reports. The Locust training module used for the framework setup is \textit{Your first test}: \url{https://docs.locust.io/en/stable/quickstart.html}.

The instructor-provided \texttt{load\_test\_tasks.py} file was preserved without modification. The separate \texttt{locustfile.py} defines a Locust user workflow with the same six workload categories: data processing, simulated database query, API request, file I/O, computation, and logging. A controlled local profile was used so that the 10,000-user test could be executed without directing high-volume traffic to the public API in the starter script.

\section{Task 2: Test Case Design}

Each Locust user repeatedly executes the six workload categories in one workflow. Locust records a separate \texttt{TASK} result for each category. The controlled API task returns a simulated response; the remaining operations perform local processing, waiting, file I/O, computation, and logging. The three baseline cases use the same standard profile and a 30-second observation window.

  --users 100 --spawn-rate 100 --stop-timeout 15

\section{Task 4: Analysis of Test Execution Results}

The 100-user and 1,000-user immediate-spawn tests completed with zero recorded failures. At 100 users, the aggregate Locust report recorded 792.579 requests per second (RPS), and at 1,000 users it recorded 7,895.465 RPS. The simulated database query and API request had low response times at these two levels. For example, the database-query average was 5.618 ms at 100 users and 5.682 ms at 1,000 users; the API-request average was 10.981 ms and 10.869 ms, respectively.

The 10,000-user test also completed with zero recorded failures. The aggregate RPS increased to 23,453.975, which shows that Locust continued to complete measured task requests. However, the response-time data changed substantially for the simulated database-query and API-request tasks. The database-query average increased to 435.702 ms with a 470.000 ms median and a 729.283 ms maximum. The API-request average increased to 445.580 ms with a 480.000 ms median and a 730.365 ms maximum. In comparison, the data-processing, computation, file-I/O, and logging task averages remained below 1 ms at the same load level.

These results show no reported execution failures, but they do show a substantial responsiveness degradation at 10,000 users for the database-query and API-request portions of the workflow. A response time near one-half second remains a completed response rather than a failure, but it is noticeably slower than the approximately 5--11 ms response times recorded at 100 and 1,000 users. Therefore, the system remained available during the 10,000-user test, while the affected workflow tasks became less responsive.

One limitation is that the workload is executed by the Locust user process itself. Consequently, the increased delay may reflect saturation of the Locust/gevent scheduling process in addition to pressure in the simulated application workload. The results identify the database-query and API-request path as the locations where the test observed degradation, but a separate application target process would be needed before attributing the full response-time increase solely to an application-service bottleneck.
