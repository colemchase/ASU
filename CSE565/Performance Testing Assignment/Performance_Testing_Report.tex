\section{Introduction}

This report evaluates the behavior of a representative multi-task workload as the requested load increases from 100 to 1,000 and 10,000 logical users. The original instructor-provided script, \texttt{load\_test\_tasks.py}, was preserved without modification. A separate benchmark runner was developed to execute the same categories of work while collecting reproducible timing, throughput, and failure measurements.

\section{Test Environment and Workload}

\subsection{Environment}

The experiments were executed on an ARM64 Apple Silicon macOS 26.6.2 computer using Python 3.14.6 on October 4, 2026. The standard benchmark profile, simulated API mode, and a maximum of 100 active worker threads were used for every scenario. The runner schedules additional logical users as workers become available. The simulated API mode intentionally avoids dependence on public-network conditions; therefore, the reported results characterize the controlled local workload rather than an external service.

\subsection{Benchmark Design}

The separate runner, \texttt{performance\_benchmark.py}, models each logical user with six sequential tasks: data processing, a simulated database delay, an API request, file input/output, computation, and logging. It limits active worker threads with \texttt{--max-workers}; consequently, a 10,000-user run represents 10,000 requested logical users without requiring 10,000 operating-system threads at once. Each user receives a distinct temporary file, and logging is synchronized to avoid the shared-file race in the starter code.

The controlled simulated API mode is used by default. This avoids sending thousands of unrequested requests to a public endpoint and makes the run more reproducible. If real API behavior is part of the experiment, identify the endpoint, timeout, date, and network conditions, and clearly distinguish those results from controlled simulated results.

\subsection{Execution Procedure}

The following command runs all required logical-user levels and produces one timestamped folder per scenario under \texttt{results/}. The default standard profile should be used consistently across the three compared runs.

\begin{lstlisting}[style=code,language=bash]
python3 performance_benchmark.py --all --profile standard --max-workers 100
\end{lstlisting}

Each result folder contains \texttt{summary.csv}, which records sample count, failures, mean, median, 95th percentile, 99th percentile, minimum, maximum, overall elapsed time, and throughput for each task. The completed result folders were preserved as evidence. The values in Tables~\ref{tab:summary} and~\ref{tab:latency} were transcribed directly from those files.

\section{Analysis}

The overall elapsed time scaled close to linearly after the smallest scenario. Increasing the workload from 1,000 to 10,000 users increased elapsed time from 0.957 to 9.421 seconds, a factor of 9.84 for a tenfold increase in logical users. Throughput increased from 847.210 users per second at 100 users to 1,061.440 users per second at 10,000 users. The smaller scenario includes thread-pool and file-system startup costs that are amortized at the larger levels. The 1,000- and 10,000-user rates are close, indicating that this controlled workload approached a stable local throughput near 1,050 users per second under the selected 100-worker limit.

The synchronized logging task was the principal latency constraint. Its mean latency increased from 13.930 ms at 100 users to 55.760 ms at 1,000 users and 60.663 ms at 10,000 users. Its P95 was also the highest of all task categories at each scenario: 37.276 ms, 62.657 ms, and 66.198 ms, respectively. The lock serializes writes to protect the shared log, so this increase is expected as more workers contend for the same resource. In contrast, data processing, computation, the simulated database delay, and the simulated API delay were stable across the larger scenarios. The controlled API task had a 10,000-user P95 of 19.409 ms, whereas logging reached 66.198 ms.

No task failures were recorded at any load level. The maximum-worker setting causes users beyond the first 100 to wait before a worker begins processing them. The per-task timings in Table~\ref{tab:latency} measure execution time after a worker starts; they do not include that initial queue wait. Consequently, overall elapsed time and throughput are the appropriate measures for the full logical-user scenarios, while the task figures identify which executed operations became slower under contention.

\section{Limitations and Recommendations}

The benchmark represents logical users on one local machine; it is not a distributed production load test. The standard profile uses a controlled API response by default, so it measures the application's workload pattern rather than a third-party service's capacity. The 100-worker cap also intentionally models bounded concurrency rather than 10,000 simultaneously active threads. For future work, use a dedicated test endpoint, execute repeated trials, graph confidence intervals or variation across trials, measure end-to-end queue waiting explicitly, and consider a distributed load-testing tool when the goal is to generate true concurrent network traffic at very high scale.

\section{Conclusion}

The controlled benchmark completed all 11,100 requested logical-user executions without recorded failures. Overall throughput stabilized near 1,050 users per second for the 1,000- and 10,000-user scenarios, while elapsed time increased nearly in proportion to the load. The shared logging operation was the limiting component because its lock-protected writes produced the largest mean and P95 latencies at higher loads. A practical next improvement is to replace the single synchronized log with buffered or asynchronous logging, then repeat the same three scenarios to determine whether the resulting reduction in contention improves sustained throughput.
